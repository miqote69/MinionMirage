# Runtime state reporting test plan

## Objective and scope

Verify that the development plugin selects the configured mapping target for the summoned Companion, waits until the game's backing contains that Companion row's own ModelChara, writes its target ModelChara and category-required customize/equipment backing once, requests the normal full redraw, applies the selected mapping's optional draw-model scale, and publishes a readable, atomic snapshot without moving Actor access outside the Dalamud Framework thread. Target switching and redraw recovery must use only Minion Mirage's own actor backing and draw path; the plugin must not inspect or invoke Penumbra, Glamourer, or any other plugin API. Type `2` DemiHuman targets must not be collapsed into the Type `3` Monster model-only path: BattleNpc targets use `BNpcCustomize` and `NpcEquip`, while EventNpc targets use `ENpcBase` customize/equipment fields or the referenced `NpcEquip`. Verify the formal product identity `Minion Mirage`: the Release output is `MinionMirage.dll`, the manifest and GUI use `Minion Mirage`, the local Dev Plugin path targets the renamed DLL, and the existing Configuration v2 language, enabled states, and target selections survive the one-time internal type-name migration. Verify the configuration UI derived from the approved local mock: it lists mapped Companion icons and localized names in the current game-data `Companion.Order` sequence, persists one enable/disable control per source mapping and each multi-option source's explicit target selection in Configuration v2, provides search and Adult Human/Young Human/DemiHuman/Monster group filters, uses one consistent accent color per group, presents card/list view selection as icon-only controls with localized tooltips, provides one enable-all and one disable-all action, and places the Automatic/English/Japanese/German/French UI-language selection inside a `Settings` menu instead of keeping it permanently visible. Each configured but unowned Companion remains in both views and in game-data order, but uses a subdued presentation, an explicit localized unowned label, and disabled per-item target/toggle controls. Ownership is read directly from the current character's `UIState.IsCompanionUnlocked` result on draw; it is not persisted, and merely displaying an unowned row must not change its stored enabled state or target choice. Companion `260` keeps one card and one ON/OFF control while only sources with two or more candidates expose an explicit combo/radio target selector; single-candidate sources retain their current display. Search matches the source and every candidate target name. The plugin window must omit the mock-only brand, runtime-status, sidebar, and large roster heading.

Failure-state accuracy is in scope. `mappings[]` reports the current selected option independently from `failedActor`, which must retain the mapping actually being applied when a normal redraw or selection-change restoration failed. A failure latch blocks additional actor writes for that same `ActorIdentity`, including after a target-selection or enabled-state change, and clears only after the failed actor leaves resolution or a different/reacquired identity appears. This uses the existing normal paths only; no target-specific failure, resolver, rollback, or write branch is introduced.

Post-apply DrawObject recreation is in scope. A tracked actor at `Redrawn` records the DrawObject pointer that completed verification. If the same game actor later receives a different DrawObject pointer, Minion Mirage resets only that tracked actor to the existing `Pending` apply stage and writes the same configured NPC again while preserving the originally captured minion appearance for mapping-disable/unload restoration. An unchanged DrawObject performs no write. No external state, collection, mod state, or plugin API is inspected.

GPose representation replacement is in scope. On GPose entry, Minion Mirage preserves the normally tracked Companion and its captured original appearance, resolves the separate GPose-visible representation from the normal Companion identity, and applies the same currently selected mapping and scale through the existing appearance pipeline to that representation. GPose handling must not restore, overwrite, or discard the normal Companion's captured original state. On GPose exit, only GPose representation tracking is released and the normal Companion path resumes. If a unique GPose representation is not available, the plugin performs no speculative write and continues observing. Normal-field summon, replacement, dismissal, mapping enable/disable, experimental summon hooks, and every protected mapping tuple are unchanged.

The Wind-up Pixie option for EventNpc `1031809` is displayed from the Japanese `ENpcResident.Singular` value `ウィン＝ニイ`, using the same full-width equals separator as the other named Pixie options. This is a label-only correction; target Row, option order, selected state, appearance path, and scale remain unchanged.

The experimental normal-summon unlock is also in scope. Its single labeled GUI switch enables the native `ActionManager.GetActionStatus` and `UseAction` hooks so every game minion icon can become usable. The status detour first calls the original function and changes the confirmed minion-hidden-area rejection `1325` to `0` for every `ActionType.Companion` Row while the switch is ON. On a Companion click, the action detour reads that exact Row's original status, then calls the original `UseAction` unchanged. When the original status was `1325`, it invokes the game's native downstream `UseActionLocation` once with the same RowId, target, and extra parameter. If that call is rejected, as observed in prohibited content, it invokes the same local Companion setup transition used by the game's Companion synchronization path with transition parameter `1`: the clicked RowId summons or replaces, while clicking the currently active Row passes RowId `0` to dismiss. No Row is queued and no automatic retry or respawn occurs. When the original status is not `1325`, the plugin returns the original result without an additional call. Minion Mirage begins appearance replacement only after the resulting Companion appears in ObjectTable. OFF disables both hooks. The path does not alter mapping configuration, conversion, or restoration. User-visible acceptance requires summon, replacement, dismissal, and the native Companion transition/VFX in the prohibited area.

Companion switches may reuse the same ObjectIndex/GameObjectId while changing BaseId before the new source model is installed. That transient state must report `source_model_pending` and must not receive either target appearance.

The escaped mapped-Companion switch/dismiss hitch is in scope. Runtime evidence shows the game can replace one Companion with another while reusing the same ObjectIndex, Actor address, GameObjectId, EntityId, and DrawObject/CharacterBase, while User observation confirms that a scaled mapped actor can visibly return toward its native scale before replacement or dismissal. Minion Mirage must therefore keep the selected target scale on the already-redrawn tracked actor for as long as that actor identity remains present, including a transient interval where the scan no longer yields a unique candidate, but write `CharacterBase.ModelScale` only when its current value differs from the requested value. It then releases the actor without writing the captured pre-conversion scale and without calling `DisableDraw` / `EnableDraw` or loading equipment on the departing actor. The game owns despawn/replacement and its native transition/VFX. Full appearance restoration remains required when the mapping is switched OFF while the same actor is still present and when the plugin unloads with that actor present. Transient loss of a unique candidate while the tracked actor and mapping remain present must retain tracking and scale without restore, recapture, or redraw.

## Environment and levels

- Static/build: Release build with Dalamud API 15.
- Static source call trace: Row `260` option B is candidate data only; trace it through the existing EventNpc resolver and the existing restore → source-model-ready → reapply path. Reject any B-specific resolver, scale, rollback, or direct-write branch.
- Runtime integration: real FF14 process, installed Dalamud Dev Plugin, standard plugin config directory.
- GPose integration: enter GPose with an already transformed mapped Companion, verify the separate visible representation receives the same selected NPC and scale, then exit GPose and verify the normal-field Companion remains correctly tracked and restorable.
- Configuration/schema: Configuration v5 persists each source mapping's enabled state, any multi-option source's selected target, and the single normal-summon experimental switch. `runtime-state.json` schema 9 reports the selected target tuple, native Companion pointers, both all-Companion native-action hooks, scope, status-bypass count, last bypassed RowId, icon-click RowId/result, and subsequent Companion observation.
- Observation: background reader opens `runtime-state.json`; it never accesses Actor pointers or invokes game actions.
- UI: actual Dalamud configuration window using the game icon texture provider and localized Companion sheet names. Static/build evidence does not replace visual review.

## Entry, suspension, and exit

- Entry: source builds and the Dev Plugin loads; valid enabled and disabled Configuration v1, valid Configuration v2 option A/B, and invalid Configuration v2 Row `260` selection inputs are available for the migration, persistence, and fallback cases.
- Suspend on plugin load failure, missing state path, invalid JSON, stale heartbeat over 5 seconds while Framework updates continue, state-writer error, Configuration v1/v2 parse or migration failure that cannot reach the defined option-B fallback, unavailable target backing, missing `BNpcCustomize` or `NpcEquip` for a Type `2` DemiHuman target, an exception from the normal `DisableDraw` / `EnableDraw` path, or inability to access the recreated `CharacterBase` for a requested model-scale write.
- Resume: after the suspension cause is resolved, reload the Dev Plugin with the same source commit and DLL SHA-256 and the affected configuration input, then resume from the affected case.
- Pass/fail authority: static/build and runtime-artifact predicates use their stated oracles; visual identity, clothing, and relative-height verdicts are separate User acceptance. For either Row `260` option, `TargetModelScale=0.7f` and an `IPluginLog` scale-write record are contract/write-request evidence only. If an existing passive post-redraw actual-scale readback is unavailable, that predicate is `UNEXECUTED`; a mapping contract value, `Redrawn`, or an `IPluginLog` scale-write record cannot establish actual applied-scale `PASS`.
- Exit: all thirteen source mappings, the Row `260` option-A/B selection contract, enabled and disabled Configuration v1-to-v2 default-B migration, persisted selection/reload and invalid-selection fallback, the static candidate-data call trace, wrong-minion, source-model pending, redraw request/failure, mapped-to-mapped switch, B-redraw and A-to-B-restore failure-state accuracy, same-identity failure latching across temporary local-player or ownership-observation unavailability, identity exit/reacquisition, despawn, unload, persisted individual and bulk enable/disable behavior, search/filter/view behavior, and `Settings`-hosted UI-language selection are distinguishable; build regression passes. Actual card/list layout, icons, labels, controls, menu behavior, and resizing require visual review in the Dalamud window.
- Regression selection: rerun the thirteen-source tuple contract, the protected scale map, the static Row `260` candidate-data call trace, all existing single-target redraw/lifecycle cases, Row `260` option-A lifecycle, the Row `260` failure-state negative branches including temporary local-player/ownership-observation unavailability with the same ActorIdentity, GPose entry/visible-apply/exit with a mapped Companion, and the existing UI controls with Row `260` selection enabled; no source mapping count, protected target tuple, existing scale, failure-time mapping, same-identity latch, normal summon/replace/dismiss behavior, or experimental summon hook may drift.
